# Product Contract

`SPDX-License-Identifier: AGPL-3.0-only`

## Status and official product

This is the complete approved TARGET contract. The current development tree closes the host-side productization path through fail-closed runtime integrity, guarded/bounded runtime resources, exact-r29 runtime generation, the explicit ARM64 tri-state capability policy, plan-first ELF rewriting, bounded near/far transformed-entry transfer planning, structural exception/unwind bridge generation and GNU unwind-index publication where discoverable, the exact 85-demo device-case specification, physical-device/evidence harnesses, and evidence-driven macOS release packaging. Hosted Verification proves those host-side invariants against the exact Go toolchain and Android NDK r29. **Physical-device execution evidence, Apple signing/notarization evidence, and an independent release review are external release facts and are not claimed as passing in the development tree.** Requirements below describe release acceptance criteria; until the external evidence gates pass, the product remains development-stage software.

The official VMPacker product is a macOS ARM64 command-line application for independent Android AArch64 ELF64 binaries. Accepted inputs are:

- Shared objects: `ET_DYN` with `PT_DYNAMIC`.
- Native executables: PIE (`ET_DYN` with `PT_INTERP`) or `ET_EXEC`.
- Android API 23 or newer.

APK, AAB, GUI, Linux release, and Windows release workflows are outside the active product. Historical APK and GUI sources under `archive/` are unsupported snapshots.

## Limits, selection, and ABI

- Input ELF size is at most 1 GiB. Manifest input must be a regular file no larger than 16 MiB. Generated bytecode is at most 256 KiB per protected function, and one invocation protects at most 4096 functions.
- Aggregate appended rewrite data is at most 1 GiB and the final planned file endpoint is at most 2 GiB.
- Function discovery uses both `.symtab` and `.dynsym`. CFG inference is fail-closed; ambiguity requires an explicit address range.
- A protected entry accepts at most 8 integer or pointer parameters and returns either `void` or one integer or pointer result. Floating-point, vector, aggregate, and variadic entry ABIs are rejected. This is an intentional binary-product boundary; the packer does not guess unavailable function type metadata.
- Calls made inside protected code implement full AAPCS64, including stack arguments, `X8`/sret, `V0`-`V7`, FP/SIMD arguments, and aggregate or complex returns.

## Instruction and control-flow correctness

- Translation uses an explicit, tested instruction whitelist. Anything outside it is rejected.
- Every decoder opcode has an explicit `virtual`, `native thunk`, or `reject` product disposition; adding an opcode without policy is a test failure.
- The whitelist includes the common FP/SIMD instructions emitted by the exact NDK r29 toolchain at `-O0`, `-O2`, and `-Oz`, as demonstrated by the maintained corpus.
- `ADR`, `ADRP`, literal `LDR`, and `BL` remain ASLR-correct after transformation.
- A transformed function entry uses direct `B imm26` when reachable. When that entry branch cannot reach, the immutable rewrite plan may use an inline `ADRP X17; ADD X17, X17, #lo12; BR X17` veneer within ADRP range. The selected function must provide at least 20 patch bytes, or 24 while preserving entry BTI; farther or shorter cases fail closed.
- Selected protected-to-protected direct tails remain VM-to-VM transfers. Explicitly validated compiler-outliner helpers may be inlined. Generic native external direct or indirect tail transfers are rejected rather than approximated as call+return.
- `UMULH` and all modeled `NZCV` effects are correct.
- Raw `SVC` execution provides full register and result pass-through.
- Native ARM64 helpers implement atomics. Load-exclusive/store-exclusive regions remain continuous native thunks; lock-based or CAS approximations are not permitted.
- C++ throw, catch, destructor, and rethrow behavior requires explicit personality/invoke/landing/LSDA and CFI integration. If a protected exception-bearing path has no discoverable `PT_GNU_EH_FRAME` route, packing fails closed. Physical Android unwinder behavior remains a release-evidence gate. Apple `__register_frame` is not used.
- `setjmp`/`longjmp` and signal-driven control-flow recovery are unsupported and must be rejected or documented as unsupported rather than approximated.

## Runtime and ELF transformation

- Embedded runtime source templates are recompiled for every pack with Android NDK revision `29.0.14206865` exactly.
- The release compiler is pinned by `.go-version`; the current canonical release toolchain is Go `1.26.0`, while the module's `go` directive retains the source-language baseline.
- The canonical public module path is `github.com/geg971509-wq/VMPackerGO`.
- Every pack creates a dynamic opcode mapping from `crypto/rand`. An explicit seed is debug/test-only and is never reported.
- Runtime bytecode/control/resource/descriptor/evaluation-stack failures are separate from architectural NZCV and terminate fail-closed after owned mappings are released; internal runtime faults are never returned as normal integer zero results.
- The architectural shadow stack is a separately mapped bounded resource with guard granules, and protected-call frame storage grows dynamically to a bounded resource limit.
- ELF rewriting is plan-first: the complete program-header, runtime-load, transformed-entry, unwind-index and relocation plan is validated before mutation. `PT_NOTE` is never hijacked.
- New load segments use `0x4000` alignment for 16 KiB compatibility. Function entries too short for safe rewriting are rejected.
- The implementation supports BTI and PAC-preserving host-side transformed-entry/call/return paths; physical CPU/kernel behavior is a release-evidence gate.
- Input, output, and report paths are distinct. The default is no-clobber; `-force` uses atomic same-directory temporary-file replacement.
- The default strips the static symbol table while preserving `.dynsym`. Debug-map output is off by default.
- Any unsupported instruction, ABI, CFG, ELF layout, relocation, rewrite condition, resource budget, or oversized bytecode descriptor fails closed without a partial-success output.

## Report target

Report v1 is implemented by the Phase 2 application boundary. A conforming JSON report has `schema_version: 1`, preserves user-supplied path text, and never exposes NDK paths, home-directory paths added by the tool, keys, seeds, or values derived from them. ## Verification and release gates

- Hosted Verification uses the exact `.go-version` toolchain, exact Android NDK r29, canonical `gofmt` enforcement, contract/evidence validator self-tests and release rehearsal, `go list`, full tests, race tests, bounded active parser/decoder fuzzing, exact-r29 FP/SIMD and whole-compiler corpora, exact-r29 runtime compilation, vet, and the macOS ARM64 CLI build.
- Release evidence comes from physical Android devices only; host and emulator results are development checks, not release gates.
- Physical-device automation covers API 23+, 4 KiB and 16 KiB page sizes, BTI/PAC behavior, dynamic loading, ASLR-sensitive paths, ABI/calls, atomics, exceptions/unwind, and transformed execution.
- All 85 approved demos must pass baseline → pack → transformed differential execution on both required physical page-size classes, with repeated equivalent results under the versioned evidence schema.
- Release artifacts are macOS ARM64 only.
- The release version is derived from and records both the Git tag and commit.
- Release binaries use Developer ID Application signing with hardened runtime and secure timestamp, followed by Apple notarization. The official artifact is a standalone Mach-O CLI; its notarization ticket is consumed online rather than falsely claimed as directly stapled to the binary.
- Each release publishes `SHA256SUMS` and the exact corresponding tagged source archive.
- Final release evidence is bound to the exact commit, device evidence and artifact/source hashes, reconstructs the tagged Git archive to reject unrelated or altered source packages, and requires a distinct independent approval.

Until every external evidence gate is reproducible and passing, the project remains development-stage software and must not publish or claim release-ready artifacts.
