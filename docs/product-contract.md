## Status and official product

This is the complete approved TARGET contract. The current development tree implements the Phase 0-3 boundary, Phase 5 host semantic fixes, an embedded-source exact-r29 validated `ET_REL` runtime, the Phase 6 host AAPCS64/native-atomic/FP-SIMD/closed-exclusive implementation, bounded unwind metadata parsing, the exact 85-demo manifest, translation preparation, the Phase 8 immutable rewrite planner, and the host-side plan applicator with structural ELF revalidation and existing transactional publication. Physical-device Phase 5/6 evidence, final veneer/unwind integration, the complete demo/device packing matrix, and release gates are not claimed as passing. Requirements below describe acceptance criteria, not current behavior.

The official VMPacker product is a macOS ARM64 command-line application for independent Android AArch64 ELF64 binaries. Accepted inputs are:

- Shared objects: `ET_DYN` with `PT_DYNAMIC`.
- Native executables: PIE (`ET_DYN` with `PT_INTERP`) or `ET_EXEC`.
- Android API 23 or newer.

APK, AAB, GUI, Linux release, and Windows release workflows are outside the active product. Historical APK and GUI sources under `archive/` are unsupported snapshots.

## Limits, selection, and ABI

- Input ELF size is at most 1 GiB, generated bytecode is at most 64 KiB per protected function, and one invocation protects at most 4096 functions.
- Function discovery uses both `.symtab` and `.dynsym`. CFG inference is fail-closed; ambiguity requires an explicit address range.
- A protected entry accepts at most 8 integer or pointer parameters and returns either `void` or one integer or pointer result. Floating-point, vector, aggregate, and variadic entry ABIs are rejected.
- Calls made inside protected code implement full AAPCS64, including stack arguments, `X8`/sret, `V0`-`V7`, FP/SIMD arguments, and aggregate or complex returns.

## Instruction and control-flow correctness

- Translation uses an explicit, tested instruction whitelist. Anything outside it is rejected.
- The whitelist includes the common FP/SIMD instructions emitted by the exact NDK r29 toolchain at `-O0`, `-O2`, and `-Oz`, as demonstrated by the maintained corpus.
- `ADR`, `ADRP`, literal `LDR`, and `BL` remain ASLR-correct after transformation; out-of-range branches use planned veneer islands.
- `UMULH` and all modeled `NZCV` effects are correct.
- Raw `SVC` execution provides full register and result pass-through.
- Native ARM64 helpers implement atomics. Load-exclusive/store-exclusive regions remain continuous native thunks; lock-based or CAS approximations are not permitted.
- C++ throw, catch, and destructor behavior is complete through explicit unwind and CFI integration. Apple `__register_frame` is not used.
- `setjmp`/`longjmp` and signal-driven control-flow recovery are unsupported and must be rejected or documented as unsupported rather than approximated.

## Runtime and ELF transformation

- Embedded runtime source templates are recompiled for every pack with Android NDK revision `29.0.14206865` exactly.
- Every pack creates a dynamic opcode mapping from `crypto/rand`. An explicit seed is debug/test-only and is never reported.
- ELF rewriting is plan-first: the complete program-header and `PT_LOAD` relocation plan is validated before mutation. `PT_NOTE` is never hijacked.
- New load segments use `0x4000` alignment for 16 KiB compatibility. Function entries too short for safe rewriting are rejected.
- The implementation supports full BTI and PAC behavior at transformed entries, calls, and returns.
- Input, output, and report paths are distinct. The default is no-clobber; `-force` uses atomic same-directory temporary-file replacement.
- The default strips the static symbol table while preserving `.dynsym`. Debug-map output is off by default.
- Any unsupported instruction, ABI, CFG, ELF layout, relocation, or rewrite condition fails closed without a partial-success output.

## Report target

Report v1 is implemented by the Phase 2 application boundary. A conforming JSON report has `schema_version: 1`, preserves user-supplied path text, and never exposes NDK paths, home-directory paths added by the tool, keys, seeds, or values derived from them. See [report-schema-v1.md](report-schema-v1.md).

## Verification and release gates

- Release evidence comes from physical Android devices only; host and emulator results are development checks, not release gates.
- Physical-device automation covers API 23+, 4 KiB and 16 KiB page sizes, full BTI/PAC behavior, dynamic loading, ASLR-sensitive instructions, ABI/calls, atomics, exceptions/unwind, and transformed execution.
- All 85 approved demos are automated and passing on the required physical-device matrix.
- Release artifacts are macOS ARM64 only.
- The release version is derived from and records both the Git tag and commit.
- Release binaries use Developer ID signing and Apple notarization.
- Each release publishes `SHA256SUMS` and the exact corresponding source.
- The placeholder Go module path is a release blocker until replaced by the canonical public module path.

Until every gate is implemented, reproducible, and passing, the project remains development-stage software and must not publish or claim release-ready artifacts.
