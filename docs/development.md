# Development

`SPDX-License-Identifier: AGPL-3.0-only`

VMPacker is currently a development-stage macOS ARM64 CLI project. It is not release-ready. The canonical public Go module path is `github.com/geg971509-wq/VMPackerGO`.

## Prerequisites

- macOS on Apple silicon.
- Go 1.26.0 for release verification; the module source-language baseline remains Go 1.21.
- Python 3.
- Android NDK revision 29.0.14206865 exactly, with its AArch64 API 23+ Clang toolchain.

Confirm the NDK before running NDK-dependent commands:

```sh
awk -F= '$1 ~ /^[[:space:]]*Pkg.Revision[[:space:]]*$/ { print $2 }' "$ANDROID_NDK/source.properties"
```

The trimmed value must be `29.0.14206865`.

## Repository checks

```sh
make packer
make runtime-integration ANDROID_NDK=/path/to/android-ndk-r29
go list ./...
go test -count=1 ./...
go vet ./cmd/vmpacker ./internal/...
go build ./cmd/vmpacker
bash -n scripts/*.sh
bash scripts/check-contract.sh
```

The default contract check covers completed Phase 0-2 product-scope and application-boundary work. Release readiness is stricter:

```sh
bash scripts/check-contract.sh --release
```

The contract guard rejects any reintroduction of the removed fixed blob, flat-blob generator, or legacy runtime-template path. The host-side implementation is present; release mode remains an explicit failure until physical-device, signing/notarization, and independent-review evidence is present.

## Current build

```sh
./build.sh
make runtime-integration ANDROID_NDK=/path/to/android-ndk-r29
```

The root build entry point may be invoked from any working directory. It builds the current Git checkout through the canonical `make mac-cli` target, verifies that the result is an executable macOS ARM64 Mach-O, and confirms both output copies are identical. NDK-dependent commands additionally require `source.properties` revision 29.0.14206865. The resulting development CLI is `dist/vmpacker-darwin-arm64` with `dist/vmpacker` as the direct runner. Runtime sources are embedded and rebuilt per invocation; the post-validation boundary requires the plan-first rewrite planner before an artifact can be produced.

Independent fixtures remain under `testdata/android/`:

```sh
make android-fixtures ANDROID_NDK=/path/to/android-ndk-r29
```

The archived APK, GUI, and packing-era snapshots are unsupported and have isolated Go modules so root traversal excludes them.

## Approved target contract

The authoritative complete target contract is [product-contract.md](product-contract.md). The following summarizes current host-verified limits; external release gates are described below.

- Input ELF size is at most 1 GiB, generated bytecode is at most 256 KiB per protected function, and one invocation protects at most 4096 functions.
- The entry ABI accepts at most 8 integer or pointer arguments and returns either `void` or one integer or pointer value. Handling of other entry ABIs is fail-closed.
- Production randomness defaults to `crypto/rand`. An explicit seed is for debug/test only and is never reported.
- Input, output, and report paths are distinct. The default is no-clobber; `-force` uses atomic same-directory temporary-file replacement.
- Unsupported instructions, malformed or ambiguous CFGs, and invalid or unsupported ELF inputs use fail-closed handling without partial-success output.
- Report v1 has `schema_version: 1` and is emitted by the application boundary with `release_ready: false` until all external release gates pass.

## Physical-device gates

Release claims require reproducible physical-device load and execution checks for API 23+, 4 KiB and 16 KiB page sizes, BTI, PAC, dynamic-linker behavior, and transformed entry/return behavior. These gates are not currently claimed as passing.

The canonical Verification workflow runs on GitHub-hosted macOS 15 ARM64 and requires Android NDK revision 29.0.14206865 exactly before product tests execute.

## Scope discipline

Do not publish artifacts from CI. Do not describe 16 KiB pages, BTI, PAC, API coverage, or device compatibility as passing until a reproducible gate demonstrates it. Unsupported extensions and broader product scope remain explicit fail-closed boundaries; expand them only with a contract change.
